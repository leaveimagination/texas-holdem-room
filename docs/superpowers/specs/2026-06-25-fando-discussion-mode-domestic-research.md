# FanDo 线下讨论模式国内实现路径调研

日期：2026-06-25

## 结论摘要

FanDo 线下讨论模式在国内可以实现。最现实的技术组合是：

- 麦克风采集：FanDo/Electron 本地采集会议室电脑麦克风。
- 实时 ASR + 说话人区分：优先接国内支持“实时说话人分离”的云服务。
- 点名触发：本地规则 + LLM 二次判断。
- 回复生成：复用 FanDo 当前 agent。
- 语音播报：接国内流式 TTS，播报期间做回声过滤。

第一期推荐优先验证两条路线：

1. 腾讯云实时说话人分离 + 腾讯云或火山/讯飞 TTS。
2. 讯飞实时语音转写大模型 + 讯飞 TTS。

如果领导非常关注数据不出本地或私有化，则并行验证：

3. FunASR/SenseVoice + CAM++/3D-Speaker 本地或私有化部署。

## 路线一：腾讯云实时说话人分离

### 能力匹配

腾讯云官方文档中有“实时说话人分离（WebSocket）”。该接口在实时语音识别基础上加入声纹聚类能力，目标是“边说边出文字边识别角色”。这与 FanDo 第一版“区分 Speaker 1/2/3，不识别真实姓名”的需求高度匹配。

腾讯云语音识别产品功能页也明确列出实时语音识别，并提到说话人分离支持分离 1 到 10 人。计费页中也单独列出“实时说话人分离”按识别时长计费。

### 接入方式

- WebSocket 建立实时识别连接。
- FanDo 将麦克风 PCM 音频按帧发送给腾讯云。
- 腾讯云返回实时识别文本、时间戳和角色标签。
- FanDo 将角色标签映射成 `Speaker 1`、`Speaker 2`。
- 点名检测命中后，把最近 3 到 5 分钟的转写上下文交给 FanDo agent。

### 优点

- 与需求贴合度最高。
- 官方能力就是实时说话人分离，不需要自己拼 ASR 和 diarization。
- 适合快速做产品 demo。
- 成本可按小时估算，便于试点。

### 风险

- 云 API 需要会议音频出网，涉及隐私和合规审批。
- 真实会议室效果依赖麦克风质量、房间混响和多人重叠说话情况。
- 供应商角色标签稳定性需要实测，尤其是多人频繁插话时。

### 适用判断

如果目标是最快做出可演示、可试点的版本，腾讯云应作为第一优先级。

## 路线二：讯飞实时语音转写大模型

### 能力匹配

讯飞开放平台的实时语音转写大模型文档中，明确提到角色分离能力，包含两种模式：

- 盲分：适用于说话人不固定、无法确认身份的场景。
- 声纹分离：适用于说话人固定、需要区分具体身份的场景。

FanDo 当前需求是“只区分不同说话人”，所以对应讯飞的“盲分”模式。

讯飞标准版实时语音转写 API 也支持 WebSocket、连续音频流、实时返回文本流；但要注意，角色分离能力应以“大模型版”文档为准，而不是只看标准版。

### 接入方式

- WebSocket 接入讯飞实时语音转写大模型。
- 发送 16k、16bit、单声道 PCM 音频流。
- 开启角色分离的盲分模式。
- 接收实时文本流、时间戳和角色信息。
- FanDo 做点名检测、上下文整理和回复播报。

### 优点

- 讯飞在中文会议、方言、远场和转写场景中积累较深。
- 大模型版支持角色盲分，正好对应“不实名，只分人”。
- 同一家供应商也提供流式 TTS，端到端采购和集成更简单。

### 风险

- 需要确认实时大模型版的商用开通、价格、并发和响应延迟。
- 标准版与大模型版能力不同，采购和技术评估时不能混淆。
- 对角色盲分结果格式、稳定性、延迟需要实测。

### 适用判断

如果会议中中文、方言、噪声和办公转写质量优先，讯飞是很强的候选路线。

## 路线三：火山引擎豆包语音

### 能力匹配

火山引擎有大模型流式 ASR API，适合实时语音识别。官方录音文件识别标准版文档中提到可启用说话人聚类分离，开启后返回说话人信息，10 人以内效果较好。

但调研到的公开文档里，实时流式 ASR 与说话人分离的组合能力需要进一步确认。换句话说：火山在 ASR 和 TTS 上都很强，但第一期如果必须“实时区分说话人”，需要验证实时接口是否支持 speaker 信息，而不能只依赖离线录音文件接口。

### 接入方式

可考虑两种：

- 实时方案：接豆包流式 ASR，如果实时返回 speaker 信息则直接使用。
- 混合方案：实时 ASR 用于字幕和点名触发，同时本地缓存音频，分段调用离线说话人聚类做回填修正。

### 优点

- 豆包语音合成支持 WebSocket 双向流式，适合 FanDo 自动语音播报。
- 生态上与大模型、实时交互、数字人等方向衔接较好。
- 适合后续做更自然的语音交互。

### 风险

- 实时 speaker diarization 能力需要商务或技术支持确认。
- 如果只能离线做说话人聚类，第一版实时 transcript 的 speaker 标签会滞后。

### 适用判断

火山适合作为 TTS 或完整语音交互方案候选；如果确认实时 ASR 可带 speaker 信息，则可进入第一梯队。

## 路线四：百度智能云语音

### 能力匹配

百度智能云语音产品页显示，实时语音识别支持 WebSocket、边上传音频边返回识别结果；音频文件转写支持多说话人分离。百度还提供智能语音会议解决方案，产品页提到支持实时转写、自动区分发言人和纪要模板。

公开文档中，“实时 ASR WebSocket”与“自动区分发言人”的产品边界需要进一步确认：是独立 API 能力，还是会议解决方案能力。

### 接入方式

- 如果实时 API 返回 speaker 信息：直接接实时 ASR。
- 如果 speaker 分离只在文件转写或会议解决方案中提供：可用实时 ASR 做字幕，离线/准实时分离做回填。

### 优点

- 百度有实时 ASR、流式 TTS、会议解决方案、端到端语音大模型等完整语音产品线。
- 如果企业已有百度智能云采购关系，可以降低商务成本。

### 风险

- 需要确认实时 API 的 speaker 信息是否开放给普通开发者。
- 如果依赖解决方案而非 API，集成灵活性可能低于腾讯/讯飞。

### 适用判断

百度适合作为备选云供应商，尤其是在已有百度云合作或希望采购会议解决方案时。

## 路线五：阿里云智能语音交互

### 能力匹配

阿里云智能语音交互支持实时语音识别，WebSocket 文档说明它能对长语音流做实时转写，并返回中间结果、标点、时间等信息。但阿里云实时语音识别接口说明明确写着：不支持说话人分离，无法进行角色分析。

阿里云在离线录音、通义听悟、FunASR/ModelScope 开源生态方面仍然有价值，但如果第一期要求“实时 speaker 标签”，单独使用阿里云智能语音交互实时 ASR 不满足需求。

### 可用方式

- 用阿里云实时 ASR 做纯转写。
- 另接本地 speaker diarization 做说话人标签。
- 或者使用 FunASR/ModelScope 私有化路线。

### 优点

- 阿里云智能语音交互产品成熟，实时 ASR、TTS、SDK 文档完整。
- 阿里开源生态里有 FunASR、SenseVoice、3D-Speaker 等可私有化组件。

### 风险

- 实时 ASR 官方不支持说话人分离，直接走云 API 不能满足核心需求。
- 拼接本地 diarization 会增加工程复杂度和延迟。

### 适用判断

不建议作为第一期“实时说话人区分”的主云方案。可以作为普通 ASR/TTS 供应商或私有化开源路线的生态来源。

## 路线六：FunASR / SenseVoice / 3D-Speaker 私有化

### 能力匹配

FunASR 是 ModelScope 生态中的工业级语音识别工具包，官方仓库介绍包含流式、说话人分离、情绪检测和 OpenAI-compatible API 等能力。SenseVoice 是多语言语音理解模型，包含 ASR、语种识别、情绪识别、音频事件检测等能力。3D-Speaker 是开源的说话人验证、识别和说话人日志工具包。

ModelScope 上也有基于 CAM++ 和聚类的说话人日志模型，说明可用于多人对话音频，自动识别对话人数并区分，适合客服对话、会议讨论、采访等场景。

### 可能架构

本地或私有化服务可以拆成：

- VAD：检测语音片段和静音。
- ASR：FunASR / SenseVoice 做语音转文字。
- Diarization：CAM++ / 3D-Speaker 做 speaker clustering。
- Punctuation：标点恢复。
- FanDo bridge：把结果转成 FanDo Discussion Mode 的 transcript segment。

### 优点

- 数据可控，可部署在内网或本机。
- 成本主要是机器资源，不按云 API 时长持续计费。
- 可以深度调参，适配会议室麦克风、行业词汇和内部术语。
- 适合有隐私要求或长期大量会议场景。

### 风险

- 工程复杂度明显高于云 API。
- 实时低延迟 + 稳定 diarization 要调很多参数。
- Windows 桌面端集成 GPU/CPU 推理、模型包分发、更新、崩溃恢复都需要额外设计。
- 真实会议室多人重叠发言仍然是难点。

### 适用判断

适合作为第二阶段或隐私版方案。若第一期就要求数据不出本地，则这是主路线，但项目周期要放宽。

## TTS 播报路线

FanDo 自动语音播报可以独立选择 TTS，不必与 ASR 同供应商绑定。

国内可选项：

- 腾讯云实时语音合成：WebSocket，支持边合成边返回音频。
- 阿里云流式语音合成：WebSocket，适合流式文本转语音。
- 火山引擎豆包语音合成：WebSocket 双向流式，适合低延迟自然播报。
- 讯飞在线语音合成：WebSocket API，流式返回音频。
- 百度流式文本在线合成：WebSocket，支持边合成边播放。

推荐第一期选择一个延迟低、音色自然、接入简单的供应商即可。若 ASR 走腾讯云，TTS 可以先用腾讯云减少账号和鉴权复杂度；若 ASR 走讯飞，TTS 可以先用讯飞。

## FanDo 集成建议

### 推荐 MVP 技术路线

优先级 1：

- ASR + 说话人区分：腾讯云实时说话人分离。
- TTS：腾讯云实时语音合成或流式文本语音合成。
- 点名检测：本地规则。
- LLM 回复：复用 FanDo 当前 agent。

优先级 2：

- ASR + 说话人区分：讯飞实时语音转写大模型，开启角色盲分。
- TTS：讯飞在线语音合成。

并行技术预研：

- FunASR/SenseVoice + CAM++/3D-Speaker 本地原型。

### 为什么这样排

FanDo 第一版最重要的是证明会议室体验成立：能实时听、能区分说话人、被点名后能自然回答。腾讯云和讯飞都能较快支撑这个 demo；本地开源路线战略价值高，但一开始容易把项目拖进模型部署和调参泥潭。

## 验证计划

第一周做供应商 spike：

- 准备 10 分钟线下会议测试音频，包含 2 人、3 人、4 人场景。
- 分别调用腾讯云实时说话人分离、讯飞实时语音转写大模型。
- 记录延迟、speaker 稳定性、中文识别准确率、多人打断表现。
- 同时测试一个 TTS 供应商的首包延迟和播放自然度。

第二周做 FanDo 原型：

- Electron 采集麦克风。
- WebSocket 推送音频到选定 ASR。
- UI 展示 Speaker 1/2/3 实时转写。
- 检测“FanDo，你怎么看？”。
- 调用 FanDo agent 并 TTS 播报。
- 播报期间过滤自身回声。

验收标准：

- 2 到 4 人线下会议中，转写延迟可接受。
- 大多数时间 speaker 标签不频繁跳变。
- FanDo 不会因为普通提及而误触发。
- FanDo 播报不会再次触发自己。
- 结束后能生成可读会议纪要。

## 主要风险

- 麦克风质量比模型选择更影响最终体验。建议演示时使用外接会议麦克风。
- 多人同时说话时，任何方案都可能出错。产品上需要提示“重叠发言，区分可信度下降”。
- 云端 ASR 涉及会议音频上传，需要明确隐私授权和数据保留策略。
- 自动语音播报要谨慎，必须点名触发，并等待自然停顿。
- 回声控制不能只靠模型，需要在产品层面记录 TTS 播放时间并过滤。
