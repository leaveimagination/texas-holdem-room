# FanDo 线下讨论模式功能设计

日期：2026-06-25

## 概述

在 FanDo 桌面客户端中新增“讨论模式”。用户点击一个按钮后，FanDo 开始通过电脑麦克风监听线下会议室里的讨论内容，实时进行语音转文字，并将不同说话人区分为 `Speaker 1`、`Speaker 2` 等标签。FanDo 平时只旁听、转写和积累上下文；只有当参会者明确点名它，例如“FanDo，你怎么看？”或“FanDo，帮我们总结一下”时，才会生成回复并自动语音播报。

第一版不做实名声纹识别，不判断某个声音真实属于谁。第一版只做当前会议内的说话人分离。用户可以在会议中手动把 `Speaker 1` 改名为真实姓名，例如“张三”。

## 目标

- 在 FanDo 桌面客户端中提供一个一键进入的线下讨论模式。
- 通过电脑麦克风采集线下会议室音频。
- 实时转写会议内容，并按说话人展示。
- 识别明确点名 FanDo 的唤醒句，再触发回复。
- FanDo 生成回复后，等待自然停顿，再自动语音播报。
- 避免 FanDo 自己播报的声音被再次转写为参会者发言。
- 会后保存有价值的会议产物：转写记录、FanDo 回复、总结、决策和待办事项。

## 非目标

- 第一版不做真实身份级别的声纹识别。
- 第一版不接入线上会议软件的系统音频。
- 第一版不做主动插话模式。
- 第一版不承诺在多人同时说话、距离麦克风较远、会议室混响严重或麦克风质量较差时仍能完美区分说话人。

## 用户体验

FanDo 主界面增加“讨论模式”按钮。点击后打开一个专注的会议面板，包含：

- 开始、暂停、继续和结束按钮。
- 当前麦克风设备和输入音量状态。
- 按说话人分组展示的实时转写内容。
- FanDo 回复区域，显示准备中的回复和已经播报的回复。
- “静音 FanDo”“暂停监听”“结束并总结”等安全控制。
- 可选的说话人重命名和合并能力。

正常流程如下：

1. 用户点击开始讨论模式。
2. 如果尚未授权，FanDo 请求麦克风权限。
3. 参会者自然讨论。
4. FanDo 实时显示转写内容，并标注 `Speaker 1`、`Speaker 2` 等说话人标签。
5. FanDo 保持安静，不主动插话。
6. 当有人说“FanDo，你怎么看？”这类明确点名句时，FanDo 将最近一段讨论上下文发送给当前配置的 agent。
7. FanDo 生成回复后，等待当前发言结束或出现自然停顿。
8. FanDo 通过 TTS 自动播报回复，并在屏幕上同步显示文本。
9. 会议结束时，FanDo 生成会议总结、决策、开放问题和待办事项。

## 触发策略

FanDo 只有在检测到明确点名时才回复。典型触发句包括：

- “FanDo，你怎么看？”
- “FanDo，总结一下。”
- “FanDo，帮我们分析一下利弊。”
- “FanDo，我们刚才决定了什么？”

第一版应采用保守策略：必须同时满足“提到 FanDo 名称”和“明显是在请求 FanDo 回答”。如果只是说“我们之后可以问 FanDo”，不应触发自动语音回复。

## 架构设计

### 讨论模式界面

负责展示会议状态。它控制会话开始和结束，显示麦克风状态、实时转写、FanDo 回复生命周期，并提供暂停、静音和结束总结等安全控制。

### 音频采集

从用户选择的电脑麦克风采集音频，并输出适合实时 ASR 和说话人分离的音频片段。它还应向界面暴露音量、静音、设备异常和音频质量提示。

### 语音处理管线

将音频转成带时间戳的文本片段。管线包含两个核心职责：

- 实时 ASR：将语音转成文本，支持临时结果和最终结果。
- 说话人分离：为每段最终文本分配稳定的当前会议内说话人标签。

管线必须保留时间戳，因为上下文窗口、自然停顿检测、会议总结和问题排查都需要时间信息。

### 唤醒句检测

消费最终转写片段，判断参会者是否明确点名 FanDo。第一版优先使用保守规则：名称匹配 + 请求式表达。检测成功后，输出触发事件，包含触发文本、说话人标签、时间戳和置信度。

### 上下文构建

当 FanDo 被点名时，构建发送给 agent 的上下文。上下文应包含：

- 最近 3 到 5 分钟的会议转写。
- 直接触发 FanDo 的那句话。
- 当前说话人标签，以及用户手动重命名后的名称。
- 当前模式说明：线下讨论场景，回复应适合语音播报，尽量简洁。
- 安全提醒：不要暴露内部实现细节。

### 回复编排器

负责协调 agent 回复和语音播报：

1. 接收唤醒事件。
2. 请求当前 FanDo/OpenClaw agent 生成回答。
3. 在界面显示“FanDo 正在准备回复”。
4. 等待自然停顿。
5. 触发 TTS 播放。
6. 将 FanDo 的回复写入会议记录。
7. 播报结束后回到监听状态。

### TTS 播报与回声控制

TTS 将 FanDo 的回复转成语音。播报时需要避免 FanDo 自己的声音被麦克风再次录入并触发转写。第一版可以采用分层方案：

- 记录 FanDo 播报的时间区间，忽略与播报区间重叠的转写片段。
- FanDo 播报时临时降低 ASR 灵敏度。
- 如果操作系统支持，优先启用声学回声消除。
- 提供设置项：FanDo 播报期间暂停麦克风转写。

## 状态机

- Idle：讨论模式未启动。
- Listening：麦克风已开启，正在实时转写。
- Addressed：检测到有效的 FanDo 点名句。
- Thinking：agent 正在生成回复。
- WaitingForPause：回复已生成，正在等待自然停顿。
- Speaking：FanDo 正在语音播报，回声抑制已启用。
- Paused：用户暂停监听或静音参与。
- Ending：正在整理转写并生成总结。
- Ended：会议产物已生成。

## 数据模型

每条转写片段应包含：

- `id`
- `sessionId`
- `speakerId`
- `speakerDisplayName`
- `text`
- `startMs`
- `endMs`
- `isPartial`
- `confidence`
- `source`：`participant` 或 `fando`

每条 FanDo 回复应包含：

- `id`
- `sessionId`
- `triggerSegmentId`
- `promptContextWindow`
- `text`
- `spokenAtMs`
- `ttsStatus`
- `agentRunId`

## 异常处理

- 麦克风权限被拒绝：界面显示权限问题，会议保持未启动状态。
- 没有可用输入设备：提示用户选择麦克风。
- 音频质量差：提示转写和说话人分离可能不可靠。
- ASR 不可用：保持界面打开，展示 provider 状态并允许重试。
- 说话人分离不可用：降级为普通实时转写，不显示 speaker 标签。
- 唤醒检测不确定：不自动语音回复，可以只在界面显示建议。
- agent 生成超时：显示简短失败提示，不阻塞继续监听。
- TTS 失败：显示回复文本，并标记语音播报失败。

## 隐私与授权

该功能会采集并处理会议音频。界面必须清晰显示录音状态。首次使用时，应提醒操作者获得参会者同意后再开启讨论模式。

默认保存策略应保持保守：

- 默认不保存原始音频，除非用户明确开启诊断模式。
- 会议结束时，经用户确认后保存转写和会议产物。
- 如果开启原始音频诊断，应显示文件保存位置，并提供清理入口。

## 产品分期

### MVP

- 讨论模式按钮和会议面板。
- 麦克风采集。
- 实时转写。
- 当前会议内的说话人标签。
- 保守的 FanDo 点名检测。
- agent 回复。
- TTS 自动播报。
- 基于播报时间区间的回声过滤。
- 会后总结。

### V1

- 说话人重命名和合并。
- 更好的音频质量提示。
- 自然停顿参数调优。
- 可配置触发短语列表。
- 会议产物导出为 Markdown 或飞书文档。

### V2

- 外接会议麦克风推荐和校准。
- 更细的说话人分离置信度展示。
- 支持决策会、头脑风暴、访谈、站会等会议模板。
- 可选集成飞书任务和飞书文档。

## 测试策略

- 单元测试点名检测：覆盖正例和反例。
- 单元测试上下文窗口选择和说话人标签格式。
- 单元测试状态流转，重点覆盖 Addressed -> Thinking -> WaitingForPause -> Speaking -> Listening。
- 集成测试模拟多说话人的转写流。
- 集成测试 TTS 播报时间区间过滤，确保 FanDo 回复不会再次触发自己。
- 使用笔记本麦克风和外接会议麦克风进行真实房间手工测试。
- 手工测试异常场景：无麦克风、权限被拒绝、ASR 失败、TTS 失败、agent 超时。

## 待定决策

- 第一版选择哪个 ASR 和说话人分离 provider。
- 会议产物第一版是否只保存在本地，还是 V1 就提供一键导出飞书文档。
- FanDo 回复前默认等待的自然停顿时间是 1.2 秒、1.5 秒，还是做成可配置项。

## 建议

第一阶段按 MVP 落地，但从一开始保留 V1 所需的架构边界。风险最高的部分是会议室真实环境下的说话人分离质量、TTS 播报期间的回声控制，以及点名触发的准确性。第一次产品演示建议使用外接会议麦克风，因为音频质量会显著影响大家对这个功能智能程度的感受。
